## Round 1 — 初版需求訪談（共 12 題）

> 初版需求草擬前的基礎訪談，確立系統定位與核心架構方向。

| #   | 問題                   | 確認答案                                                                           |
| --- | ---------------------- | ---------------------------------------------------------------------------------- |
| 1   | 使用者角色與權限       | 無需角色控管，所有可連至站台的人員均可檢視與操作                                   |
| 2   | 操作行為範圍           | 含手動觸發、暫停/恢復、啟停服務、歷史日誌；狀態變更須記錄時間與理由                |
| 3   | 資料接入模式           | Push 模式：被監控系統主動發送心跳與狀態訊息                                        |
| 4   | 訊息傳輸協定           | ZeroMQ XPUB/XSUB 模式（後於 Round 2 細化拓撲）                                     |
| 5   | 告警通知機制           | 三層：個別任務通知由被監控系統自理；盤中異常以站台 Pop-up 警告；聚合式健康確認通知 |
| 6   | 聚合通知設定方式與管道 | 第一階段於站台設定；通知管道：Email + 站台通知 + 公司內部通訊軟體                  |
| 7   | 監控規模與心跳頻率     | ~20 個系統，每系統 10~300 個排程/服務，心跳預設 30 秒，最短 1~10 秒                |
| 8   | 歷史資料保留           | 保留 30 天；無合規要求，純粹供系統人員監控使用                                     |
| 9   | 手動操作指令傳遞機制   | ZeroMQ REQ/REP 或 ROUTER/DEALER，以非同步方式處理                                  |
| 10  | 心跳超時閾值設定       | 每個排程/服務可各自獨立設定                                                        |
| 11  | 盤中時段定義           | 各系統可分別設定，第一階段預設 08:00~17:30                                         |
| 12  | 內部通訊軟體           | Microsoft Teams                                                                    |

## Round 3 — WMM 現況系統元件驗證（共 3 題）

> 依 WMM 系統實際 n Service + m ScheduledJob 組合，針對分析階段發現的疑義進行現況確認。

| #   | 問題                                   | 確認答案摘要                                                                                                                                                                                                                                           |
| --- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 32  | 服務6（外部券商 API）連線模式          | **長駐連線、非同步訊息交換**，為持續運行的 Service；確認分類為 Service，符合 FR-003 心跳超時邏輯，無需調整規格。                                                                                                                                       |
| 33  | 排程3「超限資料發 Mail」的狀態回報語義 | 回報 **`Warning`**，代表業務層面偵測到異常（資料超限）；IT 人員收到告警後，確認非資訊系統問題即可執行 Acknowledge，無需修復動作。已補充至 FR-001 Warning 語義說明。                                                                                    |
| 34  | 服務3/4/5 與 Host C 之間的心跳行為     | 透過 **MQ 低耦合**接收訊息；服務正常運行時以**固定頻率**發送心跳，心跳頻率與 Host C 訊息流量無關，符合 FR-003，無問題。                                                                                                                                |
| 35  | 服務6 監控顯示項目的建模方式           | 採**選項 B — 子指標（Sub-indicator）**：服務6 保持單一元件，心跳 payload 攜帶兩個狀態子指標（API 連線、DB 存取）及兩個數值指標（接收筆數、傳送筆數）。已新增 FR-039、FR-040。                                                                          |
| 36  | 接收/傳送筆數的計算區間                | 採**選項 A — 自服務啟動累計**：從服務啟動起計，重啟後歸零（含盤中異常重啟）。站台直接顯示心跳訊息中最後回報的數值，不在站台端累加。                                                                                                                    |
| 37  | 服務6 啟動完成/失敗的 Email 通知責任方 | **被監控系統（服務6）自行發送**，不經由監控平台。理由：若 MQ 發生異常，平台無法收到訊息，啟動結果 Email 的可靠性由被監控系統自保。符合 BI-003，監控平台不新增任何啟動通知邏輯。啟動失敗時若服務6 未推送任何心跳，平台將於超時後依 FR-003 標記為 Lost。 |

## Round 4 — WMM Sub-indicator 元件清單與訊息架構路徑確認（共 3 題）

> 依 Gap 分析結果，針對服務1/2/5 的 Sub-indicator 建模需求及 WMM 訊息路徑進行最終確認。

| #   | 問題                                          | 確認答案摘要                                                                                                                                                                                                                                               |
| --- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 38  | 服務1/2（AS400）是否需要 Sub-indicator 建模？ | **需要**。服務1/2 的心跳 payload 攜帶「AS400 連線」狀態子指標，建模方式與服務6 相同（FR-039）。AS400 連線異常時，子指標回報 `Error`，父元件狀態至少升為 Error。                                                                                            |
| 39  | 服務5（下游 MQ）是否需要 Sub-indicator 建模？ | **需要**。服務5 的心跳 payload 攜帶「下游 MQ 連線」狀態子指標，建模方式與服務6 相同（FR-039）。下游 MQ 不可達時，子指標回報 `Error`，父元件狀態至少升為 Error。                                                                                            |
| 40  | WMM 排程/服務發送至 ZeroMQ 的訊息架構路徑？   | **路徑 B 確認**：WMM 現有排程與服務以原有格式推送至 WMM 內部 MQ（舊格式）；新建立的 Adapter 服務統一從內部 MQ 讀取、轉換格式後推送至 ZeroMQ Broker；監控站台 XSUB 接收。WMM 現有系統**無需修改**訊息格式，由 Adapter 統一承擔格式轉換責任。已更新 OI-006。 |
