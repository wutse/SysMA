# 券商內部系統排程與服務監控站台 — 需求訪談記錄

> **建立日期**: 2026-04-17  
> **最後更新**: 2026-04-17  
> **對應需求文件**: `BrokerageMonitoringPlatform.requirements.md`

---

## Round 1 — 初版需求訪談（共 12 題）

> 初版需求草擬前的基礎訪談，確立系統定位與核心架構方向。

| #   | 問題                   | 確認答案                                                                           |
| --- | ---------------------- | ---------------------------------------------------------------------------------- |
| 1   | 使用者角色與權限       | 無需角色控管，所有可連至站台的人員均可檢視與操作                                   |
| 2   | 操作行為範圍           | 含手動觸發、暫停/恢復、啟停服務、歷史日誌；狀態變更須記錄時間與理由                |
| 3   | 資料接入模式           | Push 模式：被監控系統主動發送心跳與狀態訊息                                        |
| 4   | 訊息傳輸協定           | ZeroMQ XPUB/XSUB 模式（後於 Round 2 細化拓撲）                                     |
| 5   | 告警通知機制           | 三層：個別任務通知由被監控系統自理；盤中異常以站台 Pop-up 警告；聚合式健康確認通知 |
| 6   | 聚合通知設定方式與管道 | 第一階段於站台設定；通知管道：Email + 站台通知 + 公司內部通訊軟體                  |
| 7   | 監控規模與心跳頻率     | ~20 個系統，每系統 10~300 個排程/服務，心跳預設 30 秒，最短 1~10 秒                |
| 8   | 歷史資料保留           | 保留 30 天；無合規要求，純粹供系統人員監控使用                                     |
| 9   | 手動操作指令傳遞機制   | ZeroMQ REQ/REP 或 ROUTER/DEALER，以非同步方式處理                                  |
| 10  | 心跳超時閾值設定       | 每個排程/服務可各自獨立設定                                                        |
| 11  | 盤中時段定義           | 各系統可分別設定，第一階段預設 08:00~17:30                                         |
| 12  | 內部通訊軟體           | Microsoft Teams                                                                    |

## Round 2 — 需求細化訪談（共 31 題）

> 需求文件草稿完成後，針對模糊邊界與未定義行為逐題確認。

| #   | 問題                                | 選項 | 確認答案摘要                                                                                 |
| --- | ----------------------------------- | ---- | -------------------------------------------------------------------------------------------- |
| 1   | 操作人識別機制                      | A    | 無帳號驗證；開啟站台時填寫姓名存於 Session，後續操作稽核日誌自動帶入，不得為空               |
| 2   | 被監控系統初始設定方式              | C    | 初始由設定檔（appsettings.json / YAML）匯入，後續透過 UI 管理，資料存 SQLite                 |
| 3   | ZeroMQ 訊息格式規範                 | A+C  | 由獨立 Adapter 服務統一格式後推送，監控站台以鬆耦合方式接收                                  |
| 4   | 聚合健康「完成」判斷依據            | C    | 站台內起獨立背景執行緒，每隔 N 秒依指定邏輯定期檢查                                          |
| 4b  | 聚合健康判斷邏輯細化                | C    | 雙重條件：截止時間前收到 Completed 訊息 **且** 截止時間當下非 Lost，兩者缺一不可             |
| 5   | 「失聯」狀態恢復機制                | C    | 狀態自動更新回 Normal，保留失聯事件紀錄；需人工 Acknowledge 才能清除全域告警標記             |
| 6   | 聚合健康通知「未全部完成」情境      | C    | 可設定（每條規則獨立開關）：啟用時在截止到達而未完成時發送「系統異常」彙整通知               |
| 7   | Email 通知收件人設定                | B    | 每條聚合規則各自維護獨立收件人清單，透過 UI 設定                                             |
| 8   | Teams Webhook 設定粒度              | B    | 每條聚合規則各自設定獨立 Webhook URL，可發送至不同頻道                                       |
| 9   | Pop-up 多使用者處理                 | C    | Pop-up 各自關閉（僅影響自己）；需在告警中心執行 Acknowledge 才能清除全域告警標記             |
| 10  | 指令逾時後的重試機制                | A    | 逾時後顯示警告，不自動重試，由維運人員手動決定是否重新操作                                   |
| 11  | 聚合健康規則判斷週期                | B    | 可設定為每日 / 每週 / Cron 表達式                                                            |
| 12  | 資料儲存範圍                        | A    | 全部存同一個 SQLite（設定、歷史、稽核日誌、通知記錄）                                        |
| 13  | ZeroMQ 網路拓撲                     | B    | 有獨立 ZeroMQ Broker；站台以 XSUB 訂閱，被監控系統推送至 Broker                              |
| 14  | Pop-up 告警防抖機制                 | C    | 依 Acknowledge 狀態決定：未 Acknowledge 前不重複彈出新 Pop-up                                |
| 15  | 通知中心（Notification Center）行為 | C    | 兩者兼具：發出時顯示 Toast，同時記錄至持久化收件匣                                           |
| 16  | 通知中心收件匣資料保留期            | A    | 與 FR-024 一致，保留 30 天後自動清除                                                         |
| 17  | 儀表板即時更新機制                  | A    | 採用 SignalR（WebSocket），伺服器主動推送至瀏覽器                                            |
| 18  | 前端技術選擇                        | A    | Blazor Server                                                                                |
| 19  | 統一訊息格式欄位確認                | C    | 格式由 Adapter 服務團隊定義，監控站台配合接收，暫不需確認細節                                |
| 20  | 告警中心與通知中心是否同一介面      | A    | 同一介面，統一承擔告警 Acknowledge 與通知歷史查詢                                            |
| 21  | ZeroMQ 指令通道模式                 | C    | 由開發團隊依並發需求評估決定（REQ/REP 或 ROUTER/DEALER）                                     |
| 22  | SMTP 設定來源                       | C    | 沿用公司 Mail Relay，SMTP Host 寫 appsettings.json，無需帳密                                 |
| 23  | 稽核日誌操作人名稱輸入時機          | B    | 開啟站台時填寫一次，存於 Session，後續操作自動帶入                                           |
| 24  | 站台部署方式                        | C    | Kestrel self-hosted .exe，Windows 直接執行，不透過 IIS                                       |
| 25  | 異常等級與 Pop-up 觸發條件          | C    | 「失聯（Lost）」、「異常（Error）」、「告警（Warning）」三種狀態皆觸發，視覺樣式依嚴重度區分 |
| 26  | 計畫性停機的告警抑制（維護模式）    | B    | 需要；系統層級手動開啟/關閉，期間儀表板顯示「維護中」標記，抑制所有告警通知                  |
| 27  | 維護模式的稽核紀錄                  | C    | 記錄操作時間與操作人，理由**選填**（不強制）                                                 |
| 28  | 站台重啟後狀態復原                  | B    | 從 SQLite 恢復最後已知狀態，並立即對所有系統啟動心跳超時計時器                               |
| 29  | 聚合健康規則與系統對應關係          | B    | **1 對多**；一個系統可設定多條獨立聚合規則，各自有獨立任務清單、截止時間、週期與通知設定     |
| 30  | 歷史紀錄查詢維度                    | G    | 第一階段只需時間區間 + 被監控系統兩個維度                                                    |
| 31  | 維護模式對聚合健康規則的影響        | A    | 維護中系統完全豁免聚合健康判斷，截止時間到達時略過，不發送任何通知                           |
