# 券商內部系統排程與服務監控站台 — 需求確認文件

> **建立日期**: 2026-04-17  
> **最後更新**: 2026-04-18（v1.9 — 增修 Stopped 狀態支援手動停止情境）
> **狀態**: 確認完成（Q&A 已完成，含後續補充確認至 Round 9）  
> **階段**: Phase 1

---

## 1. Feature Summary

為券商內部開發一個集中式 Web 監控站台，透過 ZeroMQ XSUB 連線至獨立 Broker，接收 約 20 個證券期貨相關內部系統的即時狀態。**每個被監控系統為一個邏輯容器，由 n 個 背景服務（Service）與 m 個排程任務（Scheduled Job）組合而成，監控粒度以元件（Component）為單位**；訊息由獨立 Adapter 服務統一格式後推送。站台以 **Blazor Server + SignalR** 提供即時儀表板、異常告警（站台 Pop-up **及** Email 至系統級告警收件 人）與告警確認（Acknowledge）、手動更改元件狀態（狀態覆寫）、維護模式、操作稽 核紀錄，以及聚合式健康確認通知（Email via Mail Relay、站台通知中心、Microsoft Teams Webhook per 規則）。所有資料（設定、歷史、稽核日誌、通知）存於單一 **SQLite**，以 **Kestrel self-hosted .exe** 部署於 Windows，無需 IIS 或帳號驗證。

## 3. Functional Requirements

### 儀表板與狀態顯示

- **FR-001**：站台以儀表板形式呈現所有被監控系統的即時狀態。每個系統以群組容器方式呈現，展開後可見其所有子元件（背景服務、排程任務）的個別狀態；每個元件的狀態值為（正常 Normal、異常 Error、告警 Warning、未知 Unknown、待命 Idle、停止 Stopped、失聯 Lost、維護中 Maintenance）；系統層級狀態取所有活躍元件的最嚴重狀態（Worst-case roll-up）。
  > **Warning 狀態語義**：`Warning` 可由元件自行回報，用於表示業務層面偵測到的異常情況（例如：排程執行成功但資料超過業務閾值）。此類告警仍觸發 FR-010 的 Pop-up 與 Email 通知；IT 人員確認為業務問題（非資訊系統故障）後，可執行 Acknowledge 關閉全域告警標記，無需進行系統修復動作。`Warning` 之嚴重度低於 `Error`，但高於 `Normal`，Worst-case roll-up 排序為：**Lost > Error > Warning > Unknown > Stopped > Idle > Normal**。
- **FR-002**：監控站台透過 ZeroMQ XSUB 連線至獨立的 ZeroMQ Broker，訂閱各系統推送的狀態事件（Status Event）與週期性心跳（Periodic Heartbeat）訊息，並透過 SignalR 即時推送至 Blazor Server 儀表板。
  > **事件驅動通知機制（Event-driven Reporting）**：為確保監控即時性，當被監控系統內部（包含元根本身或其任何子指標）偵測到狀態改變（如發生異常 `Error` 或告警 `Warning`）時，**應「立即」以事件驅動方式發送狀態更新訊息至 ZeroMQ Broker**，不應等待下一次週期性的心跳排程。監控站台收到該即時訊息後，立即執行狀態卷積並觸發對應的告警流程（Pop-up & Email，參見 FR-010）。平時無狀態變更時，則維持週期性推播作為存活確認（Heartbeat）。
- **FR-003**：若心跳訊號在預設超時時間內未到達，系統自動將該**元件**標記為「失聯（Lost）」狀態並觸發告警。**對排程任務而言，Lost 判定僅適用於「執行中（Running）」狀態期間**；處於「待命（Idle）」狀態（兩次排程之間）的排程任務不受心跳超時影響，不觸發 Lost。對背景服務而言，若其處於「停止（Stopped）」狀態（因收到停止指令或回報已停止），同樣不適用心跳超時判定，不觸發 Lost。
- **FR-004**：可依系統、狀態、類型（排程/服務）進行篩選與搜尋。

### 手動操作

- **FR-005**：維運人員可在站台上手動更改各元件（排程任務或背景服務）的即時狀態（狀態覆寫），以便在特殊情況下讓整體系統狀態的邏輯判斷及顯示正確運作。（註：由站台透過 ZeroMQ 發送實際指令至排程主機或被監控服務執行的功能，移至 Phase 2 建置，Phase 1 僅於站台內更新狀態）。
- **FR-006**：(保留合併至 FR-005) 手動觸發或暫停排程的功能移至 Phase 2。
- **FR-007**：特別針對背景服務，當維運人員透過狀態覆寫手動將其標記為「停止（Stopped）」並生效後，處於此狀態下的服務預期不會發送心跳訊號，系統的超時監 控機制（FR-003）會自動略過該元件，不進行 Lost 判定。
- **FR-008**：執行任何狀態覆寫操作時，系統必須要求輸入變更理由，並自動記錄操作時間、操作人（來自 Session 姓名）、操作內容與理由（稽核日誌）。
- **FR-009**：維運人員開啟站台時，須填寫姓名作為 Session 識別，後續所有操作的稽核日誌自動帶入，無需每次重複輸入；姓名存於瀏覽器 Session，無帳號驗證。

### 告警通知

- **FR-010**：盤中某元件狀態變為「失聯（Lost）」、「異常（Error）」或「告警（Warning）」時，站台同時透過以下兩個管道發出通知：
  1. **站台 Pop-up**：警告訊息通知當前在線的使用者，視覺樣式依嚴重度區分（三種狀態各異）。
  2. **Email**：發送至該系統層級設定的個別告警收件人清單（Individual Alert Recipients）；Email 內容包含系統名稱、元件名稱、元件類型、告警狀態、發生時間。
- **FR-011**：Pop-up 告警基於 Acknowledge 狀態進行去重：同一系統若有未被 Acknowledge 的全域告警標記，不再重複彈出新 Pop-up；使用者可自行關閉 Pop-up（僅影響自己畫面），但不清除全域告警標記。
- **FR-012**：提供聚合式健康確認規則設定介面，每個系統可設定一或多條聚合規則，每條規則獨立包含：預定任務清單、預期完成截止時間、執行週期（每日 / 每週 / Cron 表達式）、Email 收件人清單、Teams Webhook URL、是否在失敗時也發送彙整通知。
- **FR-013**：當一條聚合規則所有預定任務均於截止時間前收到「Completed」狀態訊息，且截止時間當下狀態非「Lost」（雙重條件），由背景執行緒發出一次「系統正常」彙整通知。
- **FR-014**：`SendOnFailure` 旗標**僅控制外部通知（Email、Teams）的發送**，與 DailyExecution 狀態記錄及 Inbox 寫入完全解耦。截止時間到達而任務未全部符合完成條件時：若 `SendOnFailure=true`，發送「系統異常」彙整通知並說明哪些元件未完成；若 `SendOnFailure=false`，不發送外部通知，但 DailyExecution 仍記錄為 `Failed`，評估結果仍寫入通知中心收件匣（FR-020）。
- **FR-015**：彙整通知管道包含：Email（各規則獨立收件人清單，透過公司 Mail Relay 發送）、站台通知中心（Toast + 持久化收件匣）、Teams（各規則獨立 Webhook URL）。
- **FR-016**：處於「維護中」狀態的系統，聚合健康規則在截止時間到達時略過該次判斷（視為豁免），不發送任何通知。

### 告警確認與通知中心

- **FR-017**：站台提供統一的**告警/通知中心**介面，同時承擔：（1）異常告警的 Acknowledge 操作與未確認告警清單，（2）聚合健康通知的歷史記錄查詢。
- **FR-018**：維運人員在告警中心對某系統執行 Acknowledge 後，清除該系統的全域告警標記；後續若再次發生告警，可重新彈出 Pop-up。
- **FR-019**：失聯系統恢復推送心跳後，狀態自動更新為「正常（Normal）」，但保留「曾發生失聯」的事件紀錄；需維運人員在告警中心執行 Acknowledge 才能清除全域告警標記。
- **FR-020**：每次聚合健康評估完成後（無論 Success / Failed / Exempted），一律將評估結果記錄至通知中心收件匣（持久化），並顯示 Toast 即時提示；外部通知（Email、Teams）依 FR-013 / FR-014 條件獨立發送，與 Inbox 寫入解耦。即使 `SendOnFailure=false` 未發送外部通知，失敗結果仍保留於 Inbox 供站台內歷史查詢。

### 歷史紀錄

- **FR-021**：記錄各排程與服務的執行歷史（啟動時間、結束時間、執行結果、訊息內容）。
- **FR-022**：記錄所有手動操作稽核日誌（操作人姓名、時間、變更前後狀態、理由）。
- **FR-023**：記錄維護模式開啟/關閉稽核日誌（操作人姓名、時間、理由選填）。
- **FR-024**：歷史資料、稽核日誌、通知中心記錄均保留 30 天，逾期自動清除。
- **FR-025**：歷史紀錄頁面支援依**時間區間**與**被監控系統**進行篩選查詢。

### 指令傳遞

- **FR-026**：(移至 Phase 2 建置) 站台發送實際操作指令（觸發、暫停、啟停）給前端主機執行的功能。
- **FR-027**：(移至 Phase 2 建置) 發送即時非同步指令狀態追蹤及逾時未回應處理。

### 心跳超時設定

- **FR-028**：每個**元件**（背景服務或排程任務）可個別設定心跳超時閾值；對背景服務，計時從最後一次心跳起算；對排程任務，計時**僅在「執行中（Running）」狀態下**起算；超過閾值自動標記為「失聯（Lost）」並觸發告警。

### 盤中時段設定

- **FR-029**：每個被監控系統可個別設定盤中時段（起始時間、結束時間），第一階段預設值為 08:00~17:30。
- **FR-030**：Pop-up 異常告警僅於該系統設定的盤中時段內觸發；非盤中時段的異常仍記錄於站台但不彈出警告。

### 被監控系統管理

- **FR-031**：被監控系統的設定資料初始由設定檔（appsettings.json / YAML）匯入至 SQLite，後續可透過站台管理介面新增、編輯、停用。設定分為兩個層次：
  - **系統層級設定**：系統名稱、盤中時段（起始/結束時間）、**個別告警 Email 收件人清單（Individual Alert Recipients）**。
  - **元件層級設定**（每個系統可有 n 個服務、m 個排程）：元件名稱、類型（Service / ScheduledJob）、ZeroMQ Topic、心跳超時閾值；排程任務額外設定預期執行週期（Cron 表達式），供 Lost 判定窗口使用。
- **FR-032**：被監控系統可被手動設為「維護中（Maintenance）」，期間儀表板顯示維護中標記，並抑制所有告警通知（Pop-up、Email、Teams Webhook）；開啟/關閉維護模式須填寫操作人（來自 Session），理由為**選填**，操作記錄至稽核日誌。

### 站台啟動與狀態復原

- **FR-033**：站台啟動後從 SQLite 恢復各被監控系統的最後已知狀態，並依元件類型進行以下復原處理：
  - **背景服務（Service）**：恢復最後已知狀態，並立即啟動心跳超時計時器。
  - **排程任務（ScheduledJob）**，最後狀態**非 Running**：恢復最後已知狀態，不啟動計時器（計時器僅在 Running 期間啟動）。
  - **排程任務（ScheduledJob）**，最後狀態為**執行中（Running）**：執行結果因站台重啟而未知，系統立即將其轉為「告警（Warning）」並附註「站台重啟，需人工確認執行結果」，觸發標準告警流程（FR-010）；不啟動執行時間計時器，待下次排程執行時自動恢復正常生命週期。

### 聚合健康背景執行

- **FR-034**：站台內建一個獨立背景執行緒（Hosted Service），每隔 N 秒（可設定）依各 Definition 的設定進行檢查，分別針對清單中每個元件套用對應的完成條件（服務元件或排程任務元件，條件定義見 BI-008），判定 Daily Execution 實例是否達成全員完成，並於截止時間到達時發出對應通知。

### 通訊軟體整合

- **FR-035**：聚合健康通知透過各規則各自設定的 Microsoft Teams Webhook URL 發送訊息至對應頻道。

### 系統組合模型

- **FR-036**：每個被監控系統為一個邏輯容器，由 **n 個背景服務（Service）** 與 **m 個排程任務（Scheduled Job）** 組成（n + m ≥ 1）；監控粒度以元件（Component）為單位，每個元件獨立設定、獨立追蹤狀態與歷史。系統層級狀態由所有活躍元件的最嚴重狀態決定（Worst-case roll-up）。
  > **注意（共用上游依賴）**：若被監控系統內多個元件共享同一上游訊號源（例：服務3/4/5 均透過同一 MQ 接收 Host C 資料），上游故障將導致多個元件同時進入 Lost 狀態；此屬預期行為，各元件各自獨立觸發告警，平台不進行共用依賴失效的相關性分析（Phase 1 Out of Scope）。

### 個別告警 Email 通知

- **FR-037**：當任何元件的狀態於盤中時段轉換為「失聯（Lost）」、「異常（Error）」或「告警（Warning）」時，系統向該系統設定的**個別告警 Email 收件人清單（Individual Alert Recipients）**發送 Email 通知；每次告警事件發送一封（不批次合併）；Email 內容包含：系統名稱、元件名稱、元件類型、告警狀態、發生時間。

### 排程任務狀態機

- **FR-038**：排程任務的生命週期狀態遵循以下轉換：**待命（Idle）→ 執行中（Running）→ 已完成（Completed）/ 失敗（Failed）→ 待命（Idle）**。各狀態定義如下：
  - **待命（Idle）**：等待下一次排定執行時間；**不適用**心跳超時判斷，不得標記為 Lost。（於每日批次建立 Daily Execution 或收到 Idle 心跳時進入此狀態）。
  - **執行中（Running）**：正在執行，需定期發送心跳；超過心跳閾值未收到心跳則標記為 Lost。
  - **已完成（Completed）**：執行成功結束；狀態持續至下一次排程啟動前，或直到每日換日重置。
  - **失敗（Failed）**：執行異常結束；狀態持續至下一次排程啟動前（視同 Error 狀態處理），或直到每日換日重置。

### 聚合健康規則 — 定義與每日執行

- **FR-041**：現有聚合健康規則拆分為兩個獨立概念：
  - **定義（Definition）**：靜態規則範本，取代並擴展 FR-012 原有的規則設定結構。每條 Definition 包含：名稱、所屬被監控系統、**監控元件清單**（可同時包含服務元件與排程任務元件，每個元件各自適用對應的完成條件）、預期完成截止時間、執行週期（每日 / 每週 / Cron 表達式）、Email 收件人清單、Teams Webhook URL、是否在失敗時發送彙整通知，以及啟用/停用狀態。
  - **每日執行（Daily Execution）**：每條 Definition 每日由系統自動產生一筆執行實例，追蹤當日所有監控元件的完成進度與最終結果；一個 Definition 對應多筆 Daily Execution 歷史記錄。

- **FR-042**：站台背景服務在全站台統一設定的每日建立時間（`DailyExecutionCreateTime`，設定於 appsettings.json，預設 05:30）批次建立**當日所有啟用中且「執行週期」符合當日**的 Definition 的 Daily Execution 實例，初始狀態為「進行中（In Progress）」。
  > **附註（每日換日重置）**：為確保儀表板即時狀態呈現全新的一天，批次建立實例時，系統會自動將該 Definition 監控清單中的所有「排程任務（ScheduledJob）」元件的即時狀態強制重置為「待命（Idle）」；「背景服務（Service）」元件不受此機制影響，維持其由心跳驅動的狀態。

- **FR-043**：Daily Execution 實例的生命週期狀態如下：
  - **進行中（In Progress）**：實例已建立，截止時間尚未到達，任務完成追蹤進行中。
  - **成功（Success）**：截止時間到達時清單中所有元件均達成各自的完成條件（BI-008）。
  - **失敗（Failed）**：截止時間到達時任一元件未達成完成條件（含排程任務仍為 Idle 或 Running、服務出現 Error / Lost / 子指標異常）；此狀態反映客觀評估結果，無論 `SendOnFailure` 設定為何均記錄；外部通知（Email、Teams）是否發送由 FR-014 的 `SendOnFailure` 旗標獨立控制。
  - **缺失（Missed）**：截止時間已過但對應實例不存在（例如站台重啟後截止時間已到達，來不及補建）。

- **FR-044**：站台啟動時，若當日的 Daily Execution 實例尚未建立（例如重啟時間晚於 `DailyExecutionCreateTime`），系統須先比對該 Definition 的執行週期是否符合當日。若符合且對應 Definition 的截止時間**尚未到達**，則立即補建實例並標記為「進行中（In Progress）」；若截止時間已過，則建立一筆「缺失（Missed）」實例並記錄原因。若週期不符合當日，則直接略過不建立實例。

- **FR-045**：截止時間到達時，背景服務（FR-034）依 Definition 的監控元件清單，對每個元件套用對應的完成條件（BI-008）進行評估，更新當日 Daily Execution 實例的最終狀態（Success / Failed），並依設定發出彙整通知（FR-013 / FR-014）；若系統處於維護中（FR-016），略過評估並在實例上記錄「豁免（Exempted）」狀態。

- **FR-046**：站台提供**集中式聚合健康管理頁面**，可跨系統瀏覽所有 Definition 清單，以及每條 Definition 的 Daily Execution 歷史記錄（含狀態、執行日期、通知發送結果）；支援依被監控系統與日期範圍篩選。

- **FR-047**：被監控系統的設定頁（FR-031 管理介面）內嵌顯示該系統所屬的 Definition 清單，維運人員可直接在系統設定頁新增或編輯其 Definition，無需跳轉至集中管理頁面。

### 元件子指標（Sub-indicator）

- **FR-039**：元件的心跳訊息 payload 可選擇性地攜帶一組**子指標（Sub-indicator）**，每個子指標包含：
  - **名稱**（例：「API 連線」、「DB 存取」）
  - **狀態值**：僅支援 `Normal` / `Error` 兩種值
  - **數值指標（Metric）**（選填）：一個數值與標籤的組合（例：「接收筆數: 1,234」、「傳送筆數: 567」）

  子指標的狀態參與父元件的 Worst-case roll-up：若任一子指標狀態為 `Error`，父元件整體狀態至少升為 `Error`。
  當子指標狀態發生改變（如從 `Normal` 變為 `Error` 時），遵循 FR-002 的事件驅動原則，父元件應**立即**發送出該次包含最新子指標狀態的訊息，以保證站台立即發出告警通知（FR-037 / FR-010）。
  子指標本身不設定獨立心跳超時閾值，其生命週期依附於父元件；父元件被標記為 Lost 時，所有子指標一律視為失效。
  > **WMM 已知需 Sub-indicator 元件**：服務1/2（子指標：AS400 連線狀態）、服務5（子指標：下游 MQ 連線狀態）、服務6（子指標：API 連線、DB 存取；數值指標：接收筆數、傳送筆數）。

- **FR-040**：儀表板在元件列內以巢狀方式展開顯示子指標，每個子指標呈現：名稱、狀態圖示，以及數值指標（若存在）。數值指標為**自服務啟動以來的累計值**，服務重啟後歸零重算（含盤中異常重啟）；站台直接顯示心跳訊息中最後一次回報的數值，不在站台端進行累加計算。

## 4. Business Invariants

- **BI-001**：任何手動狀態變更操作必須附帶理由，系統不得允許空白理由的操作。
- **BI-002**：聚合式健康確認通知每個規則在同一個判斷週期內只發出一次，不得重複發送。
- **BI-003**：站台本身不替代被監控系統的個別任務通知，個別通知由被監控系統自行處理。
- **BI-004**：Pop-up 異常告警僅於各系統對應的盤中時段內發出，非盤中時段不得彈出告警。
- **BI-005**：(移至 Phase 2 建置) ZeroMQ 雙向指令通道設計與實作。
- **BI-006**：處於「維護中」狀態的系統，其告警通知（Pop-up、**個別告警 Email**、Teams）全部抑制，且聚合健康規則在截止時間到達時視為豆免，略過該次判斷，不發送任何通知。
- **BI-007**：同一系統若有未被 Acknowledge 的全域告警標記，不得重複彈出新的 Pop-up 告警；去重依 Acknowledge 狀態判斷，而非時間冷卻。
- **BI-008**：Definition 監控元件清單中各元件的「完成條件」依元件類型不同而異，兩類條件缺一不可：
  - **排程任務（ScheduledJob）**：截止時間前必須收到該元件的「Completed」狀態訊息，**且**截止時間當下狀態非「Lost」；截止時間到達時仍處於 Idle 或 Running 狀態視為未完成。
  - **服務（Service）**：截止時間當下元件狀態為「Normal」，**且**其所有子指標（若有）狀態均為「Normal」；任一子指標為 Error，或元件本身為 Error / Lost，視為未完成。
- **BI-009**：維運人員操作識別採 Session 姓名機制，無需帳號驗證；稽核日誌中的操作人欄位來自 Session，不得為空白。
- **BI-010**：系統層級個別告警收件人清單（Individual Alert Recipients）與聚合健康規則的收件人清單完全獨立，不得混用或共用。
- **BI-011**：排程任務的心跳超時（Lost 判定）**僅適用於「執行中（Running）」狀態**；「待命（Idle）」狀態下不得因心跳缺失而轉为 Lost。
- **BI-012**：每條 Definition 在同一日期最多只能存在一筆 Daily Execution 實例，不得重複建立；站台補建或重啟時須先檢查是否已存在。
- **BI-013**：Daily Execution 實例一旦進入終態（Success / Failed / Missed / Exempted），不得再被覆寫或重新評估；補建邏輯僅適用於實例尚未存在的情況。
- **BI-014**：Definition 監控元件清單中必須至少包含一個元件（服務或排程任務），不得為空清單；空清單的 Definition 不得被啟用。
- **BI-015**：Daily Execution 實例的建立（含每日批次與啟動補建）必須嚴格比對 Definition 的執行週期（Schedule）。只有在當前日期與執行週期匹配時，才允許建立當日的實例；不匹配的日期不得產生任何狀態（含 Missed）的實例。

## 7. Domain Vocabulary

| 術語                                             | 定義                                                                                                                 |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| **排程 (Scheduled Job)**                         | 依預定時間週期性執行的任務；生命週期與對應狀態機如 FR-038 定義                                                       |
| **背景服務 (Service)**                           | 持續運行的背景程序（如 Windows Service）；預期常時發送心跳                                                           |
| **被監控元件 (Monitored Component)**             | 被監控系統內的單一可追蹤儲位元，為一個背景服務或一個排程任務；設定、狀態、歷史均獨立管理                             |
| **心跳 (Heartbeat)**                             | 被監控系統定期發送的存活確認訊號                                                                                     |
| **聚合健康通知 (Aggregate Health Notification)** | 當一條聚合規則所有預定任務均於截止時間內達成雙重完成條件後，發出的一次性彙整狀態通知                                 |
| **稽核日誌 (Audit Log)**                         | 記錄人工操作變更的不可篡改紀錄，含時間、操作人姓名、理由                                                             |
| **失聯 (Lost)**                                  | 心跳超時未收到，系統無法確認存活的狀態；對排程任務僅在 Running 狀態下適用；恢復後需人工 Acknowledge 清除全域告警標記 |
| **待命 (Idle)**                                  | 排程任務兩次執行之間的靜止狀態；不適用心跳超時，不得轉為 Lost                                                        |
| **盤中 (In-Session)**                            | 證券/期貨交易時段，每個被監控系統可個別設定，第一階段預設 08:00~17:30                                                |
| **維護中 (Maintenance)**                         | 被監控系統手動設定的豁免狀態，期間抑制所有告警通知且聚合健康規則略過判斷                                             |
| **Acknowledge**                                  | 維運人員在告警中心確認並清除某系統全域告警標記的操作，完成後可重新觸發 Pop-up 告警                                   |
| **聚合規則定義 (Definition)**                    | 聚合健康規則的靜態範本，定義任務清單、截止時間、執行週期、通知設定等；取代舊有「規則（Rule）」概念                   |
| **每日執行 (Daily Execution)**                   | 系統依 Definition 每日自動建立的執行實例，追蹤當日任務完成狀態與最終結果（進行中 / 成功 / 失敗 / 缺失 / 豁免）       |
| **每日建立時間 (DailyExecutionCreateTime)**      | 全站台統一設定（appsettings.json）的每日實例批次建立時間，預設 05:30，所有啟用中 Definition 於此時間點同步建立實例   |
