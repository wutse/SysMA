# 券商內部系統排程與服務監控站台 — 需求確認文件

> **建立日期**: 2026-04-17  
> **最後更新**: 2026-04-17  
> **狀態**: 確認完成（Q&A 已完成，共 31 題）  
> **階段**: Phase 1

---

## 1. Feature Summary

為券商內部開發一個集中式 Web 監控站台，透過 ZeroMQ XSUB 連線至獨立 Broker，接收約 20 個證券期貨相關內部系統（涵蓋排程任務與背景服務，訊息由獨立 Adapter 服務統一格式後推送）的即時狀態。站台以 **Blazor Server + SignalR** 提供即時儀表板、異常告警（Pop-up）與告警確認（Acknowledge）、手動操作介面（觸發/暫停/啟停）、維護模式、操作稽核紀錄，以及聚合式健康確認通知（Email via Mail Relay、站台通知中心、Microsoft Teams Webhook per 規則）。所有資料（設定、歷史、稽核日誌、通知）存於單一 **SQLite**，以 **Kestrel self-hosted .exe** 部署於 Windows，無需 IIS 或帳號驗證。

## 2. Actor List

| 角色                              | 說明                                                                                                                                        |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **維運人員 (Operator)**           | 可存取站台的所有內部人員，具備完整檢視與操作權限。開啟站台時填寫姓名作為 Session 識別，無帳號驗證，所有操作稽核日誌自動帶入姓名。           |
| **被監控系統 (Monitored System)** | 主動推送心跳、執行狀態訊息至獨立 ZeroMQ Broker 的內部系統（證券/期貨相關）；訊息由獨立 Adapter 服務統一格式後發送，監控站台以鬆耦合方式接收 |

## 3. Functional Requirements

### 儀表板與狀態顯示

- **FR-001**：站台以儀表板形式呈現所有被監控系統的即時狀態，顯示各排程與服務的目前狀態（正常 Normal、異常 Error、告警 Warning、未知 Unknown、失聯 Lost、維護中 Maintenance）。
- **FR-002**：監控站台透過 ZeroMQ XSUB 連線至獨立的 ZeroMQ Broker，訂閱各系統推送的心跳與狀態訊息，並透過 SignalR 即時推送至 Blazor Server 儀表板。
- **FR-003**：若心跳訊號在預設超時時間內未到達，系統自動將該排程或服務標記為「失聯（Lost）」狀態並觸發告警。
- **FR-004**：可依系統、狀態、類型（排程/服務）進行篩選與搜尋。

### 手動操作

- **FR-005**：維運人員可手動觸發排程立即執行。
- **FR-006**：維運人員可手動暫停 / 恢復排程。
- **FR-007**：維運人員可手動啟動 / 停止背景服務。
- **FR-008**：執行任何手動狀態變更操作時，系統必須要求輸入變更理由，並自動記錄操作時間、操作人（來自 Session 姓名）、操作內容與理由（稽核日誌）。
- **FR-009**：維運人員開啟站台時，須填寫姓名作為 Session 識別，後續所有操作的稽核日誌自動帶入，無需每次重複輸入；姓名存於瀏覽器 Session，無帳號驗證。

### 告警通知

- **FR-010**：盤中系統狀態變為「失聯（Lost）」、「異常（Error）」或「告警（Warning）」時，站台主動以 Pop-up 警告訊息通知當前在線的使用者，視覺樣式依嚴重度區分（三種狀態各異）。
- **FR-011**：Pop-up 告警基於 Acknowledge 狀態進行去重：同一系統若有未被 Acknowledge 的全域告警標記，不再重複彈出新 Pop-up；使用者可自行關閉 Pop-up（僅影響自己畫面），但不清除全域告警標記。
- **FR-012**：提供聚合式健康確認規則設定介面，每個系統可設定一或多條聚合規則，每條規則獨立包含：預定任務清單、預期完成截止時間、執行週期（每日 / 每週 / Cron 表達式）、Email 收件人清單、Teams Webhook URL、是否在失敗時也發送彙整通知。
- **FR-013**：當一條聚合規則所有預定任務均於截止時間前收到「Completed」狀態訊息，且截止時間當下狀態非「Lost」（雙重條件），由背景執行緒發出一次「系統正常」彙整通知。
- **FR-014**：若聚合規則啟用「失敗時也發送通知」，截止時間到達而任務未全部符合完成條件時，發送「系統異常」彙整通知，說明哪些任務未完成。
- **FR-015**：彙整通知管道包含：Email（各規則獨立收件人清單，透過公司 Mail Relay 發送）、站台通知中心（Toast + 持久化收件匣）、Teams（各規則獨立 Webhook URL）。
- **FR-016**：處於「維護中」狀態的系統，聚合健康規則在截止時間到達時略過該次判斷（視為豁免），不發送任何通知。

### 告警確認與通知中心

- **FR-017**：站台提供統一的**告警/通知中心**介面，同時承擔：（1）異常告警的 Acknowledge 操作與未確認告警清單，（2）聚合健康通知的歷史記錄查詢。
- **FR-018**：維運人員在告警中心對某系統執行 Acknowledge 後，清除該系統的全域告警標記；後續若再次發生告警，可重新彈出 Pop-up。
- **FR-019**：失聯系統恢復推送心跳後，狀態自動更新為「正常（Normal）」，但保留「曾發生失聯」的事件紀錄；需維運人員在告警中心執行 Acknowledge 才能清除全域告警標記。
- **FR-020**：彙整通知發出時同時顯示 Toast 即時提示，並將通知記錄至通知中心收件匣（持久化）。

### 歷史紀錄

- **FR-021**：記錄各排程與服務的執行歷史（啟動時間、結束時間、執行結果、訊息內容）。
- **FR-022**：記錄所有手動操作稽核日誌（操作人姓名、時間、變更前後狀態、理由）。
- **FR-023**：記錄維護模式開啟/關閉稽核日誌（操作人姓名、時間、理由選填）。
- **FR-024**：歷史資料、稽核日誌、通知中心記錄均保留 30 天，逾期自動清除。
- **FR-025**：歷史紀錄頁面支援依**時間區間**與**被監控系統**進行篩選查詢。

### 指令傳遞

- **FR-026**：站台透過 ZeroMQ（REQ/REP 或 ROUTER/DEALER，由開發團隊依並發需求評估決定），以非同步方式向被監控系統發送操作指令（觸發、暫停、啟停）。
- **FR-027**：指令發送後，站台顯示指令執行狀態（發送中、已確認、執行失敗）；逾時未回應顯示警告，**不自動重試**，由維運人員決定是否重新操作。

### 心跳超時設定

- **FR-028**：每個排程與服務可個別設定心跳超時閾值，當超過設定時間未收到心跳，自動標記為「失聯（Lost）」並觸發告警。

### 盤中時段設定

- **FR-029**：每個被監控系統可個別設定盤中時段（起始時間、結束時間），第一階段預設值為 08:00~17:30。
- **FR-030**：Pop-up 異常告警僅於該系統設定的盤中時段內觸發；非盤中時段的異常仍記錄於站台但不彈出警告。

### 被監控系統管理

- **FR-031**：被監控系統的設定資料（系統名稱、類型、心跳閾值、盤中時段、ZeroMQ Topic 等）初始由設定檔（appsettings.json / YAML）匯入至 SQLite，後續可透過站台管理介面新增、編輯、停用。
- **FR-032**：被監控系統可被手動設為「維護中（Maintenance）」，期間儀表板顯示維護中標記，並抑制所有告警通知（Pop-up、Email、Teams Webhook）；開啟/關閉維護模式須填寫操作人（來自 Session），理由為**選填**，操作記錄至稽核日誌。

### 站台啟動與狀態復原

- **FR-033**：站台啟動後從 SQLite 恢復各被監控系統的最後已知狀態，並立即對所有系統啟動心跳超時計時器。

### 聚合健康背景執行

- **FR-034**：站台內建一個獨立背景執行緒（Hosted Service），每隔 N 秒（可設定）依聚合健康規則進行檢查，判斷各任務是否達成雙重完成條件，並發出對應通知。

### 通訊軟體整合

- **FR-035**：聚合健康通知透過各規則各自設定的 Microsoft Teams Webhook URL 發送訊息至對應頻道。

## 4. Business Invariants

- **BI-001**：任何手動狀態變更操作必須附帶理由，系統不得允許空白理由的操作。
- **BI-002**：聚合式健康確認通知每個規則在同一個判斷週期內只發出一次，不得重複發送。
- **BI-003**：站台本身不替代被監控系統的個別任務通知，個別通知由被監控系統自行處理。
- **BI-004**：Pop-up 異常告警僅於各系統對應的盤中時段內發出，非盤中時段不得彈出告警。
- **BI-005**：ZeroMQ 指令通道（REQ/REP 或 ROUTER/DEALER）與狀態推送訂閱通道（XSUB）須分開維護，不得混用。
- **BI-006**：處於「維護中」狀態的系統，其告警通知（Pop-up、Email、Teams）全部抑制，且聚合健康規則在截止時間到達時視為豁免，略過該次判斷，不發送任何通知。
- **BI-007**：同一系統若有未被 Acknowledge 的全域告警標記，不得重複彈出新的 Pop-up 告警；去重依 Acknowledge 狀態判斷，而非時間冷卻。
- **BI-008**：聚合健康規則的「任務完成」採雙重條件：截止時間前必須收到該任務的「Completed」狀態訊息，且截止時間當下該任務狀態非「Lost」，兩者缺一不可。
- **BI-009**：維運人員操作識別採 Session 姓名機制，無需帳號驗證；稽核日誌中的操作人欄位來自 Session，不得為空白。

## 5. Technology Decisions

| 項目                   | 決策                                                           |
| ---------------------- | -------------------------------------------------------------- |
| **前端框架**           | Blazor Server                                                  |
| **即時推送**           | ASP.NET Core SignalR（WebSocket）                              |
| **資料庫**             | SQLite 單一檔案（涵蓋設定、歷史、稽核日誌、通知記錄）          |
| **ZeroMQ 拓撲**        | 站台 XSUB 連線至獨立 ZeroMQ Broker 訂閱訊息                    |
| **ZeroMQ 指令通道**    | REQ/REP 或 ROUTER/DEALER，由開發團隊依並發需求評估決定         |
| **訊息格式**           | 由獨立 Adapter 服務統一轉換，監控站台以鬆耦合方式接收          |
| **Email 發送**         | 公司 Mail Relay（SMTP Host 設定於 appsettings.json，無需帳密） |
| **Teams 整合**         | 每條聚合規則各自設定獨立的 Webhook URL                         |
| **部署方式**           | Kestrel self-hosted .exe（Windows），不透過 IIS                |
| **被監控系統設定來源** | 初始由設定檔匯入，後續透過 UI 管理，資料存 SQLite              |
| **操作人識別**         | Session 姓名（開啟站台時填寫一次），無帳號驗證                 |

## 6. Out of Scope（第一階段）

- 角色權限控管（RBAC）
- 被監控系統動態自我註冊（Dynamic Registration）
- Pull 模式輪詢（主動查詢被監控系統）
- 超過 30 天的長期歸檔與合規報表
- 排程規則的新增 / 修改（僅監控，不管理排程定義）
- SMTP 帳密驗證（使用公司 Mail Relay，無需帳密）
- 操作人帳號登入驗證（採 Session 姓名識別）
- 計畫性維護的自動時段排程（維護模式僅支援手動開啟/關閉）
- 指令逾時後的自動重試

## 8. Domain Vocabulary

| 術語                                             | 定義                                                                                 |
| ------------------------------------------------ | ------------------------------------------------------------------------------------ |
| **排程 (Scheduled Job)**                         | 依預定時間週期性執行的任務                                                           |
| **背景服務 (Service)**                           | 持續運行的背景程序（如 Windows Service）                                             |
| **心跳 (Heartbeat)**                             | 被監控系統定期發送的存活確認訊號                                                     |
| **聚合健康通知 (Aggregate Health Notification)** | 當一條聚合規則所有預定任務均於截止時間內達成雙重完成條件後，發出的一次性彙整狀態通知 |
| **稽核日誌 (Audit Log)**                         | 記錄人工操作變更的不可篡改紀錄，含時間、操作人姓名、理由                             |
| **失聯 (Lost)**                                  | 心跳超時未收到，系統無法確認存活的狀態；恢復後需人工 Acknowledge 清除全域告警標記    |
| **盤中 (In-Session)**                            | 證券/期貨交易時段，每個被監控系統可個別設定，第一階段預設 08:00~17:30                |
| **維護中 (Maintenance)**                         | 被監控系統手動設定的豁免狀態，期間抑制所有告警通知且聚合健康規則略過判斷             |
| **Acknowledge**                                  | 維運人員在告警中心確認並清除某系統全域告警標記的操作，完成後可重新觸發 Pop-up 告警   |
