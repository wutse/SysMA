# 券商內部系統排程與服務監控站台 — 需求確認文件

> **建立日期**: 2026-04-17  
> **狀態**: 草稿（Open Issues 待確認）  
> **階段**: Phase 1

---

## 1. Feature Summary

為券商內部開發一個集中式 Web 監控站台，透過 ZeroMQ XPUB/XSUB 接收約 20 個證券期貨相關內部系統（涵蓋排程任務與背景服務）的即時狀態推送。站台提供即時狀態儀表板、異常告警（Pop-up）、手動操作介面（觸發/暫停/啟停）、操作稽核紀錄，以及聚合式健康確認通知（Email、站台通知、內部通訊軟體），讓維運人員即使不在電腦前也能掌握系統整體健康狀態。

---

## 2. Actor List

| 角色 | 說明 |
|---|---|
| **維運人員 (Operator)** | 可存取站台的所有內部人員，具備完整檢視與操作權限 |
| **被監控系統 (Monitored System)** | 主動推送心跳、執行狀態訊息至監控站台的內部系統（證券/期貨相關） |

---

## 3. Functional Requirements

### 儀表板與狀態顯示

- **FR-001**：站台以儀表板形式呈現所有被監控系統的即時狀態，顯示各排程與服務的目前狀態（正常、異常、告警、未知）。
- **FR-002**：監控站台透過 ZeroMQ XSUB 訂閱各系統推送的心跳與狀態訊息，並即時更新儀表板。
- **FR-003**：若心跳訊號在預設超時時間內未到達，系統自動將該排程或服務標記為「失聯（Lost）」狀態。
- **FR-004**：可依系統、狀態、類型（排程/服務）進行篩選與搜尋。

### 手動操作

- **FR-005**：維運人員可手動觸發排程立即執行。
- **FR-006**：維運人員可手動暫停 / 恢復排程。
- **FR-007**：維運人員可手動啟動 / 停止背景服務。
- **FR-008**：執行任何手動狀態變更操作時，系統必須要求輸入變更理由，並自動記錄操作時間、操作內容與理由（稽核日誌）。

### 告警通知

- **FR-009**：盤中系統發生異常時，站台主動以 Pop-up 警告訊息通知當前在線的使用者。
- **FR-010**：提供聚合式健康確認規則設定介面，可為每個系統定義「預定任務清單」與「預期完成截止時間」。
- **FR-011**：當一個系統所有預定任務於截止時間前均正常完成，發出一次「系統正常」彙整通知。
- **FR-012**：彙整通知管道包含：Email、站台通知（Notification Center）、公司內部通訊軟體（第一階段以設定方式整合）。

### 歷史紀錄

- **FR-013**：記錄各排程與服務的執行歷史（啟動時間、結束時間、執行結果、訊息內容）。
- **FR-014**：記錄所有手動操作稽核日誌（操作人識別、時間、變更前後狀態、理由）。
- **FR-015**：歷史資料保留 30 天，逾期自動清除。

---

## 4. Business Invariants

- **BI-001**：任何手動狀態變更操作必須附帶理由，系統不得允許空白理由的操作。
- **BI-002**：聚合式健康確認通知每個條件規則在同一個判斷週期內只發出一次，不得重複發送。
- **BI-003**：站台本身不替代被監控系統的個別任務通知，個別通知由被監控系統自行處理。

---

## 5. Out of Scope（第一階段）

- 角色權限控管（RBAC）
- 被監控系統動態自我註冊（Dynamic Registration）
- Pull 模式輪詢（主動查詢被監控系統）
- 超過 30 天的長期歸檔與合規報表
- 排程規則的新增 / 修改（僅監控，不管理排程定義）

## 7. Domain Vocabulary

| 術語 | 定義 |
|---|---|
| **排程 (Scheduled Job)** | 依預定時間週期性執行的任務 |
| **背景服務 (Service)** | 持續運行的背景程序（如 Windows Service） |
| **心跳 (Heartbeat)** | 被監控系統定期發送的存活確認訊號 |
| **聚合健康通知 (Aggregate Health Notification)** | 當一個系統所有預定任務於截止時間內完成後，發出的一次性彙整狀態通知 |
| **稽核日誌 (Audit Log)** | 記錄人工操作變更的不可篡改紀錄，含時間、人員、理由 |
| **失聯 (Lost)** | 心跳超時未收到，系統無法確認存活的狀態 |
| **盤中 (In-Session)** | 證券/期貨交易時段，需另行定義時間範圍 |

## Q&A 訪談記錄

| # | 問題 | 確認答案 |
|---|---|---|
| 1 | 使用者角色與權限 | 無需角色控管，所有可連至站台的人員均可檢視與操作 |
| 2 | 操作行為範圍 | 含手動觸發、暫停/恢復、啟停服務、歷史日誌；狀態變更須記錄時間與理由 |
| 3 | 資料接入模式 | Push 模式：被監控系統主動發送心跳、訊息與 Email |
| 4 | 訊息傳輸協定 | ZeroMQ XPUB/XSUB 模式 |
| 5 | 告警通知機制 | 三層：個別任務通知由被監控系統自理；盤中異常以站台 Pop-up 警告；聚合式健康確認通知 |
| 6 | 聚合通知設定方式與管道 | 第一階段於站台設定；通知管道：Email + 站台通知 + 公司內部通訊軟體 |
| 7 | 監控規模與心跳頻率 | ~20 個系統，每系統 10~300 個排程/服務，心跳預設 30 秒，最短 1~10 秒 |
| 8 | 歷史資料保留 | 保留 30 天；無合規要求，純粹供系統人員監控使用 |
